# 软著《使用说明书》强约束规范（MUST）

> 本规范由"数据采集与状态监测系统说明书大纲"提炼 + 多次用户反馈迭代而成。
> **凡涉及说明书 docx / 界面图集 HTML 的交付，以下条目均为 MUST（违反即不合格），逐条对照执行与校验。**

---

## 一、文档规模与结构（硬性指标）

| 指标 | MUST 值 |
|------|---------|
| 页数 | **30~35 页（A4）**；正文 ≥ 1.5 万字（含表格） |
| 章数 | **8 章**（标题树见下） |
| 截图位 | **≥ 30 处**（标准 37 处，与界面图集屏数**一一对应**） |
| 表格 | **≥ 10 张** |
| 术语表 | ≥ 10 项 |

### 标题树（8 章，固定结构）

```
1 引言              1.1 编写目的 / 1.2 项目背景 / 1.3 术语与缩略语（表格）
2 软件概述          2.1 软件用途（6 类） / 2.2 功能特性（表格含"对应程序实现"列）
                    / 2.3 开发环境（表格） / 2.4 软件亮点（6 条）
3 运行环境与安装    3.1 硬件环境（表格：最低/推荐） / 3.2 软件环境（表格）
                    / 3.3 安装步骤（每步配截图，标准 3 图）
4 软件使用说明      N 个小节对应软件各页面，每节 = 功能说明 + 操作步骤（每步配图）+ 结果说明
5 功能详解          M 个小节对应 core/ 各模块算法原理（公式/参数表/源码对应）
                    —— 此章是软著审查重点，**不可缺省**，每模块含"功能与源码对应表"
6 典型操作实例      2~3 个案例，每个含 6.x.1 案例背景 / 6.x.2 操作步骤（每步配图）/ 6.x.3 案例结论
7 常见问题与故障排除  8~9 条 FAQ（表格：问题现象 / 可能原因 / 解决办法）
8 技术支持          定制化服务 + 二次开发指引
附录                功能与源码对应关系表（章节 → 源码文件）
```

## 二、章节内容要点（MUST）

1. **1 引言**：编写目的（写明"本文档与《源代码文档》逐行对应、相互印证"）、项目背景（行业痛点→方案）、术语表（PMSM/FOC/MIL/HIL/SVPWM/THD/PI/RK4/REST/SQLite 等 ≥10 项，表头：英文缩写 / 中文名称 / 说明）。
2. **2 软件概述**：功能特性表**必须含"对应程序实现"列**（如：功能模块 / 说明 / 对应程序实现）；软件亮点 6 条。
3. **3 运行环境与安装**：硬件环境表（最低/推荐两列）、软件环境表（依赖库/版本/说明）、**安装三步（解压→装依赖→启动）每步配一张截图**。
4. **4 软件使用说明**：每节重构为三段式——
   - **4.N.1 功能说明**（H3）：该页面作用 + 界面元素 + **每个参数逐项解释**；
   - **4.N.2 操作步骤**：STEP(1)(2)(3)… **每一步都配一张截图位**；
   - **4.N.3 结果说明**：操作后界面呈现什么、指标含义。
   - 要求"**每个操作步骤都要有截图，截图要多**"。
5. **5 功能详解**：9 个小节左右对应 core/ 模块，每节：算法原理（文字化公式 + 参数表）+ **功能与源码对应表**（功能点 / 实现文件 / 核心函数），章末"功能详解小结"给出源码导航。
6. **6 典型操作实例**：案例含背景/步骤（每步配图）/结论；章末**案例结果汇总表**。
7. **7 FAQ**：9 条左右，覆盖安装（乱码/依赖/端口占用）、运行、数据异常等。

## 三、截图位与图集一一对应（MUST）

- 说明书每个"图 N"图位，界面图集 HTML 必须有**同号同题**的一屏（`<div class="fig" id="figN">`）。
- 截图位清单（标准 37 处）分配：3 章安装 3 图（终端界面）→ 4 章使用说明约 26 图（每操作步骤）→ 6 章案例约 8 图。
- **正文引用一律写"如下图所示"**，禁止硬编码"如图 N 所示"（防止与自动编号错位）。
- 图题格式：「图 N 标题」居中加粗，下附占位说明（"界面截图，此处插入：xxx"）。

## 六、功能与源码一一对应（MUST，软著审查核心）

- **正文叙述每项功能时，自然融入对应源文件与函数名**（例："弱磁策略由 core/foc.py 的 FOCController.step 实现"）。
- 附录必须给出**功能与源码对应关系表**（说明书章节 → 源码文件/函数）。
- 要求"**所有功能的实现要与源代码文件所实现的功能一一对应，能相互印证**"——写完后用源代码文档交叉检查，不能有"文档写了但源码没有"的功能，反之亦然。

## 七、用户强约束清单（历次反馈沉淀，MUST）

1. **页数 30~35 页左右**，内容详尽，不能过于简洁。
2. **4 章软件使用说明**：既要有功能说明（功能介绍），也要有操作步骤并**每步配截图**，截图要多。
3. **5 章功能详解不能缺**（用户原话"你好像还缺一个功能详解页面"）。
4. **功能与源码一一对应、可相互印证**（见第六节）。
5. **安装步骤每一步可以插入截图**；4 章每个操作步骤都要有截图。
6. **界面图集**：每屏必须呈现**该界面的所有内容**（不是"相关内容"）；必须是**真实运行界面**（不是示意拼贴/占位文字/近似布局）。
7. **终端/命令行类截图**：必须是**独立终端窗口**（黑底 cmd，含标题栏/菜单栏），**禁止套进软件侧栏+主区域布局**（用户原话"为什么是在软件界面里会有终端命令行？"）。
8. 图集与说明书图位**逐屏一一对应**（同号同题）。
9. 文档交付后若用户指出问题，按"现状核实 → 修改方案 → 影响范围 → 优先级"四段式回应。

## 八、程序化校验（交付前 MUST 全部通过）

1. `check_manual_docx.py`（或等价脚本）复验：箭头符号 0 / `**` 0 / 非黑 0 / 斜体 0 / **图题数 = 图位数**。
2. 统计：图题 ≥ 30、表格 ≥ 10、正文字数 ≥ 1.5 万、估算页数 30~35。
3. 图集 `validate_html.py` 通过：屏数 = 图注数 = 锚点数 = 说明书图位数。
4. 图集图表初始化脚本：正则提取全部 init IIFE → `node --check` 语法 → **stub 环境实际执行零异常**（防 `series[0]` 类未定义变量导致整图空白）。
5. 源代码文档 `check_src_doc.py`：文档 ↔ 磁盘源码**逐行一致**。
6. 全部通过后才 `present_files` 交付。
