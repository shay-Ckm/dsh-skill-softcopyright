# 软著/论文文档降 AIGC 率方案（MUST 参考）

> 由"数据采集与状态监测系统说明书"降 AIGC 实战沉淀（第一轮 84 段词汇级语义重构，AI 高频词合计降幅 74%；第二轮 6 处句式结构级改写，结构性残留清零）。
> 由"面向STM32的FOC算法模型在环测试与自动部署软件说明书"二轮实测补齐（第三轮 PaperPass 标红段落精修：1 轻+5 中+5 重全部改写清除，复测通过）。
> **适用场景**：交付的说明书 docx、源代码文档 docx 等正文存在明显 AI 写作痕迹时，按本方案改写与验证。
> 目标：让文本更像人写的——高困惑度、句长有波动、无模板套话、无 AI 句式结构，**同时不破坏既有格式约束与功能↔源码对应**。

## 〇、三轮递进策略（先词汇，再结构，后实测驱动）

| 轮次 | 层面 | 目标 | 手段 | 实测效果 |
|------|------|------|------|---------|
| 第一轮 | 词汇级 | 清 AI 高频词/模板套话 | 语义重构 + 补细节 + 长短句 + 删套话 | AI 高频词 100→26（降 74%）/ 85→29（降 66%） |
| 第二轮 | 句式结构级 | 清 AI 句式结构 | 按"结构性问题清单"21 类逐类修复 | 结构性残留清零 |
| 第三轮 | 实测驱动 | 按检测平台标红段落精修 | 打破排比/拆超长句/口语化衔接/变主语 | PaperPass 1轻+5中+5重全部清除 |

**判断顺序**：先跑词汇级（check_aigc.py），再跑结构级（check_aigc.py --struct），词汇结构清完后**交给用户用检测平台实测（PaperPass/知网 AIGC/维普等），按标红报告做第三轮精修**。静态检测清"共性问题"，实测平台抓"语言顺滑度"，两者互补——静态检测全过 ≠ 实测通过，最终以实测为准。

## 一、AIGC 检测器在看什么（原理）

| 检测指标 | 含义 | AI 文本特征 | 人类文本特征 |
|---------|------|------------|-------------|
| 困惑度 Perplexity | 语言模型对文本的"意外程度" | 低（65~80），用词太顺滑 | 较高（85~120），有意外用词 |
| 突发性 Burstiness | 句长/节奏的波动程度 | 句长均匀、节奏单调 | 长短句交错、节奏有起伏 |
| 语言风格指纹 | 高频词 / 过渡词 / 句式分布 | "首先/综上所述/值得注意的是"、模板句、过度平滑衔接 | 用词朴素、衔接自然多样 |

**结论**：降低 AIGC 率 ≠ 换同义词。有效手段是 **语义重构 + 补具体细节 + 长短句交错 + 删模板套话 + 个人化口吻 + 清 AI 句式结构**。

## 二、AI 高频词与模板句式清单（检测命中即改写）

### 高频词（出现即优先替换/删改）
```
本系统、本软件、同时、此外、因此、其中、从而、通过、实现、采用、进行、提供、
支持、用于、以便、旨在、值得注意的是、综上所述、首先、其次、最后、一方面、
另一方面、随着、不仅、而且、具备、具有、充分、有效、显著、重要、相关、相应、
合理、便捷、直观、一站式、该功能由…实现、能够有效、为用户提供
```

### 模板句式（整句重构，不保留框架）
- "该功能由 xxx.py 的 xxx() 函数实现" → 改为"计算放在 core/analysis.py 的 fft_spectrum 函数里"（自然融入源码名，同时满足功能↔源码对应）
- "本系统提供 xxx 功能" → 直接陈述功能本身，去掉"本系统提供"前缀
- "通过 xxx 实现 xxx" / "采用 xxx 方法" → 改被动为主动陈述："信号用包络谱来解调，先带通滤波…"
- "旨在/值得注意的是/综上所述" → 删除或替换为口语化承接

## 三、中文 AI 味结构性问题清单（第二轮，MUST 逐类检查）

> 来源：stop-slop/structures + Humanizer-zh + 社区众测，经本项目实测适用。**毒不在句式本身，在用法**：技术文档里"不是X而是Y"描述客观对比（如"不是无故障，而是特征被噪声盖住"）是合理的；下面每种要**先判断是否 AI 味再修**。

### 3.1 "不是A而是B"三毒（最高优先级）
| 毒型 | 特征 | 示例 | 修法 |
|------|------|------|------|
| 毒1 假靶子 | 前半句否定一个根本没人做过的判断 | "AI 改变的不是工具，而是生产关系" | 删前半句，只留 B |
| 毒2 同义替换 | A 和 B 是同一个意思，换高级说法 | "不是在演风，而是在演失控感" | 合并成一句 |
| 毒3 无关硬凑 | 不需要转折处强行"不是而是" | "数据本身反而不是稀缺品；真正的关口在于——" | 直接说 B（"数据量上来了，麻烦也跟着来"） |
| NNY 变体 | "不是X。不是Y。只是Z。" | "不是错误，不是特性，而是根本的设计缺陷" | 删掉前两项，直接说 Z |

### 3.2 二元对比（制造虚假戏剧性）
"X不是问题，Y才是" / "答案不是X，是Y" / "感觉像X，其实是Y" / "问题不是X，而是Y" / "不再是X，开始成为Y" / "不仅X，而且Y"（"不仅是技术，更是艺术"）→ **直接说 Y，或两者并列**。

### 3.3 否定列举（修辞性拖延）
"不是X...不是Y...是Z" / "没有X，没有Y，只有Z" → 直接说 Z。

### 3.4 戏剧性碎片化
"X。就这样。就是这个。" / "X。而且Y。而且Z。" / "这一刻，X" → 用完整句子、合并、删掉用动作收尾。（技术文档极少见，命中即删）

### 3.5 修辞性设置（宣告洞察而非传递洞察）
"如果...呢？" / "我的意思是：" / "想想看：" / "这也没关系。" → 直接阐述。

### 3.6 公式化结构
"首先...其次...最后..."（三段式）→ 用隐性连接（"说到这里""另一方面"）；"随着...的发展" → 直接说发生了什么；"在...的背景下" → 直接说背景事实；"从某种意义上说" → 删掉直接说；"值得注意的是/需要指出的是" → 删掉直接说内容。

### 3.7 虚假能动性（无生命物体做人事）
"X变成了Y" / "X存在或消亡" / "X浮现" / "X转变" / "X告诉我们" / "X奖励" → 指明真实行为者（"数据告诉我们"→"某人阅读数据后得出结论"）。
> **注意**：软件说明书中"系统/页面/后端提供、完成、支持"是**行业标准表达**（描述软件职责），不属 AI 味，**不要机械改写**——实测误改会破坏技术文档的规范性。

### 3.8 距离化叙述者（上帝视角）
"没有人设计过这个。" / "这是因为..."（讲师口吻） / "人们往往会..."（社会学家口吻） / "这正是..."（宣告式，如"这正是检验算法抗噪能力的地方"→"抗噪能力好不好一试便知"）→ 用场景/细节/具体主语。

### 3.9 被动语态（隐藏行为者）
"X被创造了" / "人们认为" / "错误被犯了" / "决定被做出了" / "噪声被压下去" → 指明行为者或改主动（"去噪后随机噪声明显减弱，故障冲击反而保留"）。
> 技术文档的被动语态（"数据被加载""文件被解析"）是规范表达，**只改叙述性段落**中的被动，不改技术描述。

### 3.10 节奏问题
- 三项目列表过度（"A、B、C"连续顿号）→ 用两个或一个；**技术参数枚举（轴承参数、特征频率清单）保留**；
- 问题被立即回答 → 留思考空间或删掉；
- 每个段落都以有力结尾 → 变化结尾方式；
- 连续句子长度相同 → 打断其中一个，长短交错；
- 连续短句堆叠 → 合并或加入长句。

### 3.11 词汇模式
- 懒惰的极端词：每个、总是、从不、所有人、没有人 → 用具体细节代替；
- 副词过度：突然、好像、瞬间、其实、实际上 → 删掉或用具体描写；
- 同义词循环（AI 重复惩罚导致过度换词）→ **允许自然重复**。

## 四、改写手法（逐条 MUST）

1. **语义重构而非换词**：整句重组语序、变换主语、改句式（陈述句↔祈使句↔条件句），让语言模型无法通过词级替换对齐。
2. **补具体数据与细节**：加真实数字、单位、实测口吻（例："0 HP 对应 1797 rpm、1 HP 对应 1772 rpm…"），具体性是人类写作的强信号。
3. **长短句交错**：长句拆短（>60 字的超长句必须拆），短句（<15 字）刻意保留；目标句长标准差 ≥ 0.4（人类 0.4~0.7，AI <0.3）。
4. **删模板套话**：清除"一站式/值得注意的是/综上所述/首先其次最后"等检测器高频命中词。
5. **个人化/口语化点缀**：少量"说几点实测体会""把信号拷出来粘进 Excel 慢慢算"等第一人称或操作口吻，注意保持学术/说明书文体不失专业。
6. **保护技术名词与规范表达**：算法术语（如"显著峰""谱尖锐度"）不因撞词就改写；软件说明书里"系统/页面提供、支持"等职责描述、技术参数的被动语态、参数枚举列表，都是规范表达，**保留**。
7. **句式结构逐类清扫**：按第三节 3.1~3.11 清单逐类正则扫描 → 判断是否 AI 味 → 命中即按修法改写。

## 五、程序化流程（建议顺序执行）

```
1. 分析（check_aigc.py）→ 输出：AI 高频词计数、模板句式命中、句长分布（均值/标准差/最长句）
2. 结构扫描（check_aigc.py --struct）→ 输出：3.1~3.11 各类句式命中段落，逐一判断是否 AI 味
3. 定位 → 列出含 AI 痕迹词的正文段落（跳过标题/图题/步骤/表格）
4. 改写 → 构建 {原文子串: 改写文本} 映射表，用"子串匹配"（非全文匹配）逐个替换，
   鲁棒性更好；每条改写保留技术内容与格式
5. 复验 → ① AI 高频词降幅统计（目标：合计 ≥ 50%）
           ② 结构性问题复扫（目标：命中数 0）
           ③ 格式约束复验（check_manual_docx.py：箭头 0 / ** 0 / 非黑 0 / 斜体 0）
           ④ 结构完整性（图题数=图位数、表格数、8 章标题树不变、段落数一致）
           ⑤ 功能↔源码对应关系未改动
6. 后处理 → 保存前全文清理残留箭头/emoji（改写文本可能引入"→"）
```

### 改写脚本要点（实测）
- **用子串匹配**：`if old in para.text: para.text = para.text.replace(old, new)`，比全文等值匹配命中率高（实测 84/84 全命中，全文匹配只有 21/23）。
- **样式保留**：python-docx 中 `run.text` 改写会保留该 run 的字体/字号/颜色，改写后段落格式（首行缩进/行距）不受影响；**优先改写整段的首个 run**，避免多 run 拆分导致样式丢失。
- **跨 run 兜底**：若子串跨多个 run（`old` 不在单个 run 中），拼合整段 run 文本 → 替换 → 写回首 run、其余 run 置空（实测第一轮 84 条中有跨 run 情况，需兜底）。
- **保存前清箭头**：改写文本里不要用"→"，写流程用顿号或"之后"。

## 六·五、第三轮：实测驱动精修（PaperPass/知网标红段落）MUST

### 触发
用户反馈检测平台（PaperPass/知网 AIGC 检测/维普等）标红结果（常分级：轻度/中度/重度疑似 AIGC）。

### 标红段落的共同特征（实测 11 段归纳）
1. **句式整齐的列举/功能描述**：`"A 包含…；B 包含…；C 包含…"` 式排比（如三份 C 代码各文件职责、六项指标逐一罗列）；
2. **功能点平铺**：`① 新工况扩展：可依据…；② …` 模板化枚举；
3. **长句完整度高**：200+ 字一气呵成、逻辑完备、无停顿；
4. 术语密集但语言"太顺滑"——内容真实（这是技术文档难点：不能造假，只能改表达）。

### 改写手法（第三轮，逐条 MUST）
| 手法 | 示例（前 → 后） |
|------|-----------------|
| 破排比、换主语、变判断句 | "FOC_Control.h 头文件包含…；FOC_Control.c 源文件包含…" → "**FOC_Control.h 是头文件，…都在这；FOC_Control.c 装…**" |
| 拆超长句（>100 字必拆） | 240 字引言首段 → 3 个短句（"读完就能上手"） |
| 口语化衔接 | "避免命令行编码问题" → "省得命令行编码出乱子"；"软件自动识别" → "软件会自己识别" |
| 破 ①~④ 模板 | "可依据 X 接口新增…" → "想加新工况，顺着 X 接口补…" |
| 叙述转判断/条件句 | "供与仿真对照，验证一致性" → "拿来和仿真对照，看看差多少"；"以…判定" → "看…是否在 5% 以内" |

### 保留项（不得动）
源码函数名与文件路径、术语括号定义（PMSM/FOC/MIL）、公式与点乘号（`Rs·i_q`）、技术数值（2205 rpm/5%/2% 带宽）、`①~④` 序号本身、图位结构。技术准确性零改动。

### 工程坑（已实测）
1. **检测平台贴文 ≠ docx 实际文本**：PaperPass 报告复制的段落与文档存在**空格/点乘号差异**（`5% 判定` vs `5%判定`、`10% 至 90%` vs `10%至 90%`、`Rs·i_q` vs `Rs i_q`）→ 改写子串必须按 **python-docx 提取的实际 p.text** 对齐，别直接抄检测报告；
2. **未命中检查必须在改写前做**（改写后再检查会把已替换子串误报为未命中）；
3. 用户预览打开文件时保存被锁 → 逐级 `_V2~_V10` 另存兜底；
4. 多轮产物命名递增：`_降AIGC版.docx` → `_V2` → `_V3`；
5. 术语密集的"算法原理"段落（弱磁/前馈公式等）易命中轻度/中度——这类段落改写空间有限，**可接受适度疑似**，不必强求清零（清到重写公式就得不偿失）。

### 复验（第三轮）
① 标红原文逐段探针检查"残留=0"；② check_aigc.py 降幅/结构扫描；③ 段落/图题/表格数与改前全等；④ check_manual_docx.py 格式约束全过；⑤ 交付 `_降AIGC版_V2.docx` 等，等用户复测反馈。

## 七、与本技能其他规范的配合

- 改写后**必须重跑 `check_manual_docx.py`**（格式约束）+ 人工确认功能↔源码对应表未删改。
- 若改写导致功能↔源码对应关系需要更新（一般不会，改写只动叙述不动功能），按 manual-spec.md 第六节交叉检查。
- 交付物命名：`<软件名>说明书_降AIGC版.docx`，与正式版并存，用户选其一使用。
- **图位占位符注意**：若用户已手动编辑过说明书（如删改占位说明），图题数 ≠ 占位符数是**用户编辑版现状**，降 AIGC 不改动图位结构；复验时以"改写前后段落/图题/表格数不变"为准，不要强行补齐占位符。
