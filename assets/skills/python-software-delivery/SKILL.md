# Python 软件项目全流程交付

## 何时使用
- 用户提出"做一个 xx 系统/上位机/工具/软件"，需要从零开发并交付可运行源码。
- 软著/毕设/比赛场景，要求产出《使用说明书.docx》《源代码文档.docx》、界面图集、源码压缩包。
- 核心难点是信号处理/数据分析/算法类项目（如振动、图像、点云、传感器数据），需配套可视化与诊断。

## 流程总览（**每阶段结束必须 Checkpoint 中断，等用户审阅后再继续**）

一次交付依次执行五个阶段。**铁律：任何阶段/子步骤完成并校验通过后，立即停下汇报结果，等待用户明确回复"继续/可以"才进入下一阶段；禁止一口气跑完全部流程。** 用户工作流习惯是分阶段放行（常回复"继续吧"）。

1. **需求确认** → ✔ Checkpoint：展示 4 项决策结果，等用户确认后开工
2. **开发** → ✔ Checkpoint：核心功能可演示后停下（如打开运行中的服务 + 关键测试结果），等审阅
3. **回归测试** → ✔ Checkpoint：汇报准确率/达标率与误判明细，等审阅
4. **源码打包** → ✔ Checkpoint：汇报打包产物清单与冒烟验证结果，等审阅
5. **文档交付** → **每份文档单独 Checkpoint**：说明书 docx 生成并复验后停下等审阅；图集截图生成并**回填说明书 docx**（图题数 == 图片数）后停下等审阅；源代码文档 docx 生成并校验后停下等审阅；用户要求降 AIGC 时，改写复验后停下等审阅；需要 AIGC 证明文档时，两份 docx 生成并复扫后停下等审阅；全部确认后再统一交付（串联关系见下节）

Checkpoint 汇报格式（精简）：已完成内容 + 校验结果（量化）+ 下一步计划 + 等待确认。若用户沉默或只说"继续吧"，仅推进到下一个 Checkpoint，不得连续跨越多个阶段。

## 技能串联：软著交付流水线（本会话实证，2026-09-27）

本技能是**编排方**，其余三个技能是它各阶段调用的下游。串联链路：

| # | 阶段 | 调用技能 | 输入 | 产物 | 完成判据（不满足即未完成） |
|---|---|---|---|---|---|
| 1 | 需求确认 | 本技能 Phase 1 | 用户需求 | 4 项决策 | 用户确认 |
| 2 | 开发 | 本技能 Phase 2 | 决策 | 可运行服务 + 前端 | API 联调 + 浏览器实测无 JS 异常 |
| 3 | 回归测试 | 本技能 Phase 3 | 代码 | 回归报告 | 多种子×多工况断言全过 |
| 4 | 源码打包 | 本技能 Phase 4 | 代码 | zip + sdist + start.bat | 开发树冒烟 + **发布包冒烟（干净目录）** |
| 5 | 使用说明书 docx | 本技能 Phase 5.1 | 源码 AST + 规范 | 说明书（含「图 N」图位） | 格式复验全过 + 真实渲染页数 |
| 6 | **界面图集 + 回填说明书** | **`manual-ui-screenshots`** | 说明书图位清单 + 运行中的服务 | `docs/atlas/figNN.png` + **插图版说明书 docx** | 图题数 == 图片数；残留占位段 0；md5 全唯一 |
| 7 | 源代码文档 docx | 本技能 Phase 5.3 | 源程序目录 | 源代码文档 | 逐行比对 22/22 一致（按技能脚本口径） |
| 8 | 降 AIGC（按需） | **`aigc-review-reduction`** | 说明书 docx | `..._降AIGC版.docx` | AI 高频词降幅 ≥50% + 结构/格式复验全过 |
| 9 | AIGC 申诉证明（按需） | **`software-copyright-aigc-appeal`** | 说明书 + 源程序目录 | 哈希清单 + 研发日志 docx | 哈希数 = 源文件数；四处口径一致 |
| 10 | 统一交付 | 本技能 Phase 5.6 | 全部产物 | 交付清单 | present_files 打开关键产物 |

**串联铁律**：

1. **界面图集不是独立交付物**：第 6 步的完成判据是**插图版 docx**，不是"图集 HTML 已生成"。只交 HTML 时审查方看到的说明书仍是空图位（此前发生过，用户明确要求改为直接插入）。
2. **三个下游技能自带 Checkpoint**：调用它们时同样遵守"每份产物校验通过即停下汇报、等用户确认"的铁律，不要因为"这是子技能"就一口气跑完。
3. **四处口径必须一致**（软著送审硬要求）：源程序目录 = 源代码文档封面 = 哈希清单 = 研发日志 → **同一组「N 个源文件 / M 行代码」**。任何一步收窄范围，其余三处同步改。
4. **降 AIGC 只改文字、不动结构**：图题数、图片数、表格数、章节标题树必须保持不变（改完复跑 `check_manual_with_figs.py`）。
5. **第 8、9 步按需触发**：用户提"降 AIGC/查重优化"走第 8 步；收到"AIGC 检出率高"补正通知走第 9 步；两者常一起出现（先降率、再备证明）。
6. **著作权人等法律事实不代填**：证明文档里的著作权人、研发周期等以用户提供的为准，生成时留占位符并明确请用户确认。

## Phase 1 需求确认
收到任务后先用 `AskUserQuestion` 一次问清 4 个关键决策（每项给推荐项并放第一位）：
1. **技术形态**：Flask Web（可复用 CSS/ECharts，截图演示方便，推荐）/ PyQt 桌面；
2. **数据来源**：内置模拟器 + 支持导入公开数据集（推荐，离线可演示）/ 仅模拟 / 必须真实数据集；
3. **核心功能深度**：自动诊断/分析结论（推荐）/ 仅分析工具；
4. **数据存储**：SQLite 历史记录（推荐）/ 不保存。
确认后再开工；答案影响整个架构，勿自行假设。

## Phase 2 开发
- **环境**：用托管 Python 建独立 venv（`python -m venv`），依赖全部装进 venv，绝不污染系统环境；前端库（ECharts 等）下载到项目 `static/` 本地化，离线可用；国内源优先清华镜像。
- **模块划分**：后端入口 + 数据库 + `core/` 核心算法包。核心算法按领域拆模块（如信号分析/诊断/数据解析/硬件接口预留），每模块一个文件、函数职责单一。
- **后端**：REST API 风格，采集+分析合并为一个接口返回完整结果（含降采样绘图数据），历史记录 CRUD 接口齐全。
- **前端**：单页应用，深蓝侧边栏 + 白色卡片 + 主题色 `#1677ff`（Ant Design 系）；图表用 ECharts 本地版；绘图数据后端降采样（时域 ≤4000 点、频谱 ≤2400 点）控制传输量。
- **前端运行时验证（必做）**：curl 只能验证 API 与页面可达，**发现不了前端 JS 运行时错误**（ECharts 图表键名不一致如 `charts.speed` vs `chartSpeed`、动态生成脚本引用未定义变量如 `series[0].markLine` → 整图空白）。交付前：① `node --check` 对 app.js 做语法检查；② 对动态生成的全部图表 init 脚本，用 stub（假 echarts/document/window/setTimeout）实际执行确认零 ReferenceError；③ 有浏览器时优先截图验证界面。
- **Windows 关键坑**：见 references/dev-notes.md。

## Phase 3 回归测试
- 对核心算法做**多随机种子 × 多工况**的批量回归（如 5 工况 × 15 种子 = 75 例），统计准确率并打印误判明细。
- 同时测边界工况（弱故障/强噪声）：应表现为**保守漏报**（判"疑似/正常"）而非误报。
- 算法调优以实测谱统计为准（如峰值/中位数比、显著峰门槛），勿凭感觉定阈值。

## Phase 4 源码打包
1. 写 `pyproject.toml` + `MANIFEST.in`（资源清单含 templates/static/start.bat），`python -m build --sdist` 生成 tar.gz；
   （`python -m build` 需先 `pip install build`，否则报 `No module named build`；它会在项目根生成 `*.egg-info/`，属构建元数据，打包脚本须排除、打包后清理）
2. 用 Python zipfile 生成同名 `.zip`（Windows 友好，内含安装说明）；
   **运行包必须包含运行时必需的前端库（如 echarts.min.js）**："排除 *.min.js 等第三方压缩库"的规则**仅适用于源代码文档 docx（gen_src_docx.py）**，不得用于 zip/sdist 运行包，否则交付的应用图表空白；
3. 打包前清理运行时文件（`records.db`、`__pycache__`、`uploads/`、临时文件）；
4. 一键启动 `start.bat`：**必须纯 ASCII**（含中文会因 GBK 解析乱码报"不是内部或外部命令"）+ 解释器选择链（项目 .venv → 托管 venv → 系统 python）+ 依赖缺失自动 `pip install -r requirements.txt -i 清华镜像`；
5. 写《安装与启动说明.md》（环境要求/安装/启动/FAQ/目录结构）；

### ⚠️ P0 打包陷阱：`_*` 前缀排除规则会吞掉 `__init__.py`（实测 2026-09-22，电池BMS平台）

本项目诊断产物统一以 `_` 开头（`_*.txt`/`_*.js`），打包脚本遂用 `EXCLUDE_FILE_PREFIX = ("_",)` 一刀切排除。
**`__init__.py` 同样以下划线开头，被一并排除**，且包内 `__init__.py` 数量从 12 掉到 **0**。
最致命的不是少了 12 个文件，而是：`bms_platform/utils/` **目录内仅有一个 `__init__.py`**，
该文件被排除后 zipfile 不再写入任何条目 → **整个目录从包里消失** →
交付包启动即报 `ModuleNotFoundError: No module named 'bms_platform.utils'`，
而**开发树内一切正常**（Python 3 命名空间包兜住了其余目录），属"本地测不出、客户一装就挂"型故障。

**规则**：
- 排除 `_*` 时**只作用于非 .py 文件**（`fn.startswith("_") and not fn.endswith(".py")`），并保留 `__init__.py` 白名单；
- 打包脚本**必须内置完整性守卫**：遍历源程序目录下全部 `.py`，与待打包清单逐个比对，缺任一文件即 `sys.exit(1)` 拒绝出包（不要只比对文件数，目录整体消失时数量差往往不显眼）；
- 顺带排除 `*.egg-info` / `*.dist-info` 构建元数据目录。

### 验证（两步都要做，缺一不可）

**第一步 · 开发树全模块冒烟**：跑通核心链路各模块公开入口，逐项记录通过率。
注意：冒烟脚本自身的 API 名/导入写错会被误判成"产品缺陷"——每处失败都要回源码核对
真实字段名/方法签名，确认是脚本错才改脚本（实测一轮 6 处失败中 6 处全是脚本自身错，
如 `sp.impedance`→`sp.z_magnitude`、`c.threshold`→`c.swap_threshold`、漏 import 等）。

**第二步 · 发布包冒烟（干净目录，必做）**：把 zip 解压到系统临时目录，
**把冒烟脚本也复制进去，以该目录为 cwd 运行**，彻底脱离开发树。这一步专抓
"开发树能跑、交付包不能跑"的丢包/路径/资源缺失问题。至少覆盖：
- 必需文件与**每个 Python 包目录都有 `__init__.py`**（`static/`/`templates/` 等纯资源目录不需要）；
- 全部 `.py` 可 `py_compile` 编译；
- 核心链路端到端；
- 导入 Web 入口（起仿真线程）→ 用 `test_client` 遍历全部**页面路由**与 **API 路由**，
  断言 200 且 JSON；
- 关键接口的**字段完整性**（可兼作前期界面修复项的回归守卫）；
- 前端库经 Flask 可访问（`/static/lib/*.min.js` 返回 200 且非空），模板经 `url_for` 引用本地库；
- 源码无硬编码开发机绝对路径。

**第三步（可选但强推荐）· 真实 HTTP 启动**：`cmd /c start.bat` 常被沙箱拦截（"Invoking cmd.exe from Bash bypasses all command validation"），
替代做法：执行与 `start.bat` **最后一行完全一致**的命令（`<选定解释器> bms_platform/web/app.py`），
并对 `start.bat` 做静态校验（纯 ASCII 字节数、解释器链、依赖自检行）。
若解压目录没有 .venv 又不想拷贝数 GB 依赖，可在解压目录建轻量 venv 后用 `.pth`
（写入项目 venv 的 site-packages 路径）复用依赖，即可跑通真实启动。
访问本地服务务必绕过系统代理（见 `references/dev-notes.md`）。

## Phase 5 文档交付（软著三件套）

> **⚑ 强约束**：说明书的结构（8 章标题树）、内容要点、截图位清单（≥30，标准 37，与图集一一对应）、表格清单（≥10）、格式规范（A4/字体/无箭头/全黑无斜体）、功能↔源码一一对应、程序化校验，全部见 **`references/manual-spec.md`**，逐条 MUST 执行，不满足即视为未完成。

### 5.1 使用说明书 docx
- 参考用户提供的说明书 docx：用 python-docx 解析其格式规范（页面/标题/正文/缩进/字体），严格照抄（见 references/docx-format-spec.md）。
- **结构 = manual-spec.md 第一节 8 章标题树**；4 章每节三段式（功能说明 / 操作步骤每步配图 / 结果说明）；5 章功能详解**不可缺省**（软著审查重点，每模块含功能↔源码对应表）。
- **功能↔源码一一对应（可相互印证）**：正文叙述每项功能并自然融入对应源文件与函数名；附录给"功能与源码对应关系表"。
- **用户强约束**：30~35 页、安装步骤每步配图、4 章每个操作步骤配图（截图要多）、无 emoji/箭头符号、无彩色（Heading 默认蓝色需显式设黑）、无斜体、无 Markdown 符号（**）、图位以"图 N 标题 + （界面截图，此处插入：xxx）"预留。
- 生成后**程序化校验**（check_manual_docx.py）：符号 0、** 0、非黑 0、斜体 0、图题数与截图位数一致 + 统计页数达标。
- **页数务必用真实渲染取值**：`manual_stats.py <docx> --render`（Word COM 后台渲染取 `ComputeStatistics(2)`，本机已装 Word + pywin32，约 16 秒）。**不要用"每页 1400 字"经验法**——实测含表格/图位的稿件约 751 字/页，旧经验法会低估近一半并误判"需增补"。详见 `references/dev-notes.md` 的「说明书页数怎么数」。
- **✔ Checkpoint**：复验通过后停下，汇报图位数/表格数/字数/真实页数，等用户审阅再继续图集。

### 5.2 界面图集并回填说明书（技能串联：`manual-ui-screenshots`）
**本步骤的完成标准是「插图版说明书 docx」，不是"图集 HTML 已生成"。** 说明书里的「图 N」只是占位段（「（界面截图，此处插入：xxx）」），图集不回填，审查方拿到的仍是空图位。

- **路径判定（先做）**：软件能启动 → **首选真实运行截图**（Playwright + 本机 Chrome 驱动运行中的服务，界面与数据全真）；跑不起来但有前端源码 → 真实界面还原路径；只有文档 → 按描述重建。详见该技能 Step 0。
- **屏数 = 说明书图位数**，逐屏同号同题一一对应；截图尺寸固定 2559×1559。
- **每屏必须呈现该界面的所有内容**（不是"相关内容"）；禁止示意拼贴/占位文字/近似布局。
- **终端/命令行类图位独立渲染**（黑底 cmd 独立窗口，标题栏+菜单栏），**禁止套进软件侧栏+主区域布局**；命令行内容取自**真实命令输出**，路径用真实 `C:\Users\...`。
- **成对图必须内容互补（易翻车）**：2559×1559 视口下页面往往不滚动，滚顶/滚底会拍成两张同 md5 的图（Word 插图时还会去重，表现为"图题 37 图片 36"）。对策：正文面板统一 `document.body.style.zoom='1.5'` 后再滚顶/滚底，首页/总览用 100% 拍整体布局；脚本末尾 **md5 唯一性校验必过**。
- **交付前校验**：validate_html.py / validate_atlas.py（容器↔图注↔锚点一致）+ **图表 init 脚本 stub 执行零异常**（防未定义变量整图空白）。
- **回填说明书（MUST）**：`insert_atlas_into_manual.py <说明书.docx> docs/atlas --expect N --backup` 按「图 N」图题上方插入居中图片（页宽 14.6 cm，等比）+ 删除占位段；随后 `check_manual_with_figs.py <docx> --expect N` 要求 **图题数 == 图片数**、图号连续、残留占位段 0。重跑前先从 `_仅图位版.docx` 备份恢复，否则二次插入。
- **插图会显著增加页数**（实测 45 → 60 页，约每图 0.4 页）：用户对页数有约束时，**先确认再插图**（插图后压页数代价更高）。
- **✔ Checkpoint**：插图版复验通过后停下，汇报"屏数 = 图位数、图题数 = 图片数、插图后页数"，等用户审阅后再继续源代码文档。

### 5.3 源代码文档 docx
- 用 `scripts/gen_src_docx.py` 将全部手写源码按参考格式排入一个 docx（文件标题黑体小四加粗、代码正文宋体 10.5pt + Times New Roman、行距 1.05）；
- **封面必须标注代码规模**：「共 N 个源文件，M 行代码」（N/M 由脚本自动统计，供审查快速核对体量）；
- **只收录手写源码（强约束）**：`EXCLUDE_DIRS` 必须排除 `docs/`、`img/` 等交付物目录和 `tmp_*` 临时目录——否则 3MB 级界面图集 HTML（内联 echarts 单行 98 万字符）会被当源码收录，docx 撑到 500+ 页（已实测事故）；单行超长(>5000字符)文件自动跳过并告警；生成后抽查"超长段落数"应为 0；
- 排除第三方压缩库（如 echarts.min.js）；
- **软著场景源程序范围（强约束，2026-08-21 用户明确要求）**：源代码文档/源码包只收**软件本体运行源码**（入口/配置/core 业务/前端 templates+static/css+js），**排除 `tests/` 测试文件与 `scripts/` 开发辅助工具**（打包/文档生成/校验/图集等——与软件运行无关，软著审查不接受测试与工具脚本凑行数），排除 docs/img/tmp_*/第三方压缩库/说明 md；**材料生成脚本**（gen_proof_docx、stats_source_hashes、rewrite_aigc*、scan_struct*、gen_manual_content、gen_ui_atlas 等）放项目根 scripts/，**禁止混入源程序目录**；最稳妥做法：以发行版解压包目录为源并核对 scripts/ 内容；**源程序目录、源代码文档封面、哈希清单、研发日志四处文件数/行数必须一致**（实测 29/4338 → 26/4103 → 17/2324 两轮收窄）；打包脚本 EXCLUDE_DIRS 同步排除 `tests`+`scripts`（运行包保留 echarts.min.js 的规则不变）；
- **C#/.NET 软著项目（实测 2026-08-22，一测定音电机测试平台）**：多源剔除清单 = `bin/`（NuGet 第三方 dll/exe/pdb + deps.json）、`obj/`（cache + 自动生成的 AssemblyInfo.cs/GlobalUsings.g.cs + project.assets.json）、`.vs/`、`Properties/`（launchSettings.json IDE 配置）、`wwwroot/bootstrap/`（第三方压缩库 min.css+.map）、`wwwroot/favicon.png`（第三方图标）、README.md（说明文档）；保留 = 手写 `.cs/.razor/.razor.css/.csproj` + `appsettings*.json` + 手写 `wwwroot/app.css` + `.sln`；打包与文档用**同一收集模块**（src_collect.py）保证同源；校验用"docx 标题集 vs zip basename 集"严格比对，勿用正则硬匹配（双扩展名 `.razor.css`、含点文件名 `appsettings.Development.json` 会误报缺失）；注意 Demo 与 Web 可同名 `Program.cs`（46 文件/45 唯一名属正常）；校验正则只需 `\.(cs|razor|csproj|json|css|sln)$` 判标题段；
- 用 `scripts/check_src_doc.py` 逐行比对文档↔源码，必须全部"一致"再交付。
- **✔ Checkpoint**：校验通过后停下，汇报文件数/代码行数/一致率，等用户审阅。

### 5.4 降 AIGC 率（技能串联：`aigc-review-reduction`，可选/按需）
> **触发**：用户要求"降低 AIGC 率/降 AI 痕迹/查重优化"等。**优先直接调用技能 `aigc-review-reduction`**（它自带 `check_aigc.py`、`probe_residue.py` 与标红报告解析流程，检测口径比本节脚本更全）；完整方案与改写手法另见 **`references/aigc-reduction.md`**（MUST），检测平台与查重方式见 **`references/aigc-detection-platforms.md`**。
>
> **输入通常是插图版说明书**（Phase 5.2 的产物）。改写只动文字，**图题数/图片数/表格数/章节标题树必须保持不变**——改完必须复跑 `manual-ui-screenshots/scripts/check_manual_with_figs.py` 确认「图题数 == 图片数」仍成立。
- **三轮递进**：第一轮清词汇级（AI 高频词/模板套话，降幅 ≥50%）；第二轮清句式结构级（21 类结构性问题清单复扫残留 0）；第三轮**实测驱动**——用户用检测平台（PaperPass/知网 AIGC/维普）实测后，按标红段落（轻度/中度/重度疑似）精修，直至复测通过。静态检测清共性问题、实测平台抓"语言顺滑度"，**最终以实测为准**。
- **分析**：`scripts/check_aigc.py <docx> --old <原版> --struct --list`——输出 AI 高频词计数、模板句式、句长分布（突发性）、结构性问题扫描（21 类 AI 句式命中段落）、列举式长句参考指标、改写目标段落、与旧版降幅对比。
- **改写**：构建 {原文子串: 改写文本} 映射表，**子串匹配**逐段替换（比全文等值匹配命中率高，实测 84/84）；手法 = 语义重构（非换词）+ 补具体数据细节 + 长短句交错 + 删模板套话 + 少量个人化口吻；第三轮针对标红段另加：破排比（"A 包含…；B 包含…"→"A 是…，…都在这；B 装…"）、拆超长句（>100 字必拆）、口语化衔接（"省得…出乱子"）；跨 run 子串需拼合整段文本改写（实测需兜底）。
- **保护技术名词与规范表达**：算法术语（"显著峰"）不因撞 AI 词就改写；软件说明书里"系统/页面提供、支持"等职责描述、技术参数被动语态、参数枚举列表、公式点乘号（`Rs·i_q`）、技术数值是规范表达，**保留**——结构扫描命中后需人工判断是否真 AI 味。
- **工程坑（实测）**：检测平台贴文 ≠ docx 实际文本（空格/点乘号差异）→ 子串必须按 python-docx 提取的实际 p.text 对齐；未命中检查必须在改写前做；用户预览打开文件保存被锁 → 逐级 `_V2~_V10` 另存。
- **后处理**：改写文本禁箭头"→"（用顿号/"之后"），保存前全文清理残留箭头/emoji。
- **复验（量化）**：词汇级 AI 高频词合计降幅 ≥ 50%（实测 74%/66%）；结构性问题复扫残留 0；结构完整性（图题/表格数/段落数不变）；标红原文逐段探针检查残留=0；重跑 `check_manual_docx.py` 格式约束全过（箭头/**/非黑/斜体 0）。
- **✔ Checkpoint**：每轮复验通过后停下，汇报降幅/结构数据与产物名，等用户审阅（用户实测后再按标红段落精修，一般循环 1~2 轮达标）。
- 交付物命名：`<软件名>说明书_降AIGC版.docx`；多轮改写递增 `_V2`/`_V3`。若用户已手动编辑过说明书导致图题≠图位，属用户编辑版现状，降 AIGC 不改图位结构。

### 5.5 AIGC 申诉证明文档（技能串联：`software-copyright-aigc-appeal`，按需）
- **触发**：软著申请收到"AIGC 检出率高"补正通知，或用户要求备好"独创性真实开发"证明材料。
- **调用该技能**生成两份 docx：①源程序文件目录结构及哈希值清单（每文件 SHA-256）；②项目研发日志。核心约束：
  - **以发行版解压包为源程序口径**（不是开发树，避免混入 records.db/uploads/__pycache__/egg-info）；
  - **哈希清单文件集 = 源代码文档封面文件数**，行数口径与 `gen_src_docx` 一致 → 四处数字（源程序目录/源代码文档封面/哈希清单/研发日志）必须一致；
  - 研发日志写成"做决策"口吻、**禁止以"实现 xxx"开头**，写入真实函数名/接口路径/配置项以便交叉核验；生成后跑 AI 高频词复扫（残留 0）。
- **著作权人/研发周期等法律事实不代填**：留占位符并请用户确认后批量替换（脚本映射，勿手改几十处）。

### 5.6 最终交付
